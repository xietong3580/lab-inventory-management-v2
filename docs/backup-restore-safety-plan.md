# 数据库备份恢复与回滚安全方案

> 版本：V2/V3 Step 10-7A
> 更新时间：2026-07-03
> 适用范围：库存自动化管理系统 数据库备份恢复预检与回滚流程

---

## 1. 为什么需要恢复/回滚功能

库存系统作为正式替换旧库存系统的长期稳定系统，数据正确性是最高优先级。

可能出现需要恢复/回滚的场景：

1. **批量录入错误** — 录入 300+ 产品后发现部分数据有误，但难以逐一修正
2. **误清空操作** — 意外执行了清空测试业务数据
3. **数据库损坏** — SQLite 文件因异常关机、磁盘问题导致损坏
4. **错误导入** — 从旧系统导入数据时发生了未预期的覆盖
5. **安全事件** — 需要回滚到被篡改之前的状态

恢复/回滚的目标：
- 快速恢复到已知安全的时间点
- 最小化数据丢失
- 操作可审计、可追溯

---

## 2. 备份与恢复的风险

### 备份风险
- 备份频率不足，导致回滚时损失过多数据
- 备份文件损坏未被及时发现
- 备份文件被误删除
- 备份文件存储在不可靠的介质上

### 恢复风险
- **覆盖风险**：恢复时错误覆盖了正确的当前数据库
- **选错文件**：恢复时选择了错误或损坏的备份文件
- **权限风险**：未经授权的用户执行恢复操作
- **审计缺失**：恢复操作事后无法追溯是谁在什么时候做了什么
- **服务中断**：恢复过程中业务不可用

### 缓解措施
- 每批重要操作前创建备份
- 恢复前先执行预检（Step 10-7A 已实现）
- 恢复前自动再备份当前数据库
- 严格权限控制（仅 admin）
- 恢复操作记录审计日志
- 恢复后执行维护安全检查

## 3. 当前 10-7A 状态：仅恢复预检

### 已实现

| 功能 | 接口 | 说明 |
|------|------|------|
| 恢复候选列表 | `GET /api/maintenance/restore-candidates` | 列出 backups 目录下的 .db / .sqlite 文件 |
| 恢复预检 | `GET /api/maintenance/restore-preflight?filename=xxx` | 对指定备份做只读检查 |

### 恢复预检内容

1. **文件存在性检查** — 备份文件是否存在
2. **文件大小检查** — 大小是否 > 0
3. **SQLite 可打开检查** — 使用只读模式（`mode=ro`）尝试打开
4. **PRAGMA integrity_check** — 数据库完整性校验
5. **关键表存在检查** — products / transactions / audit_logs / users
6. **核心数据量统计** — 产品数、出入库记录数、审计日志数、用户数

### 安全约束

- ✅ 所有检查使用 SQLite 只读模式
- ✅ 文件名严格校验，禁止路径穿越
- ✅ 仅允许 .db 和 .sqlite 扩展名
- ✅ 文件必须位于备份目录下
- ✅ 仅 admin 可访问
- ✅ 不覆盖当前数据库
- ✅ 不执行真实恢复
- ✅ 不返回绝对路径给前端

### 未实现

- ❌ 真实恢复执行接口
- ❌ "一键恢复数据库"按钮
- ❌ 备份文件删除功能
- ❌ 自动恢复调度

## 4. 未来真实恢复接口设计约束

当需要开发真实恢复功能时，必须满足以下所有条件：

### 前置条件
1. **admin 权限** — 仅管理员可执行
2. **恢复前自动备份** — 在覆盖当前数据库前，先创建当前数据库的备份（安全网）
3. **二次确认** — 用户必须输入确认短语（如"确认恢复数据库"）
4. **明确显示恢复目标** — 显示文件名、备份时间、数据统计
5. **预检通过** — 必须先通过 restore-preflight 检查
6. **审计日志记录** — 记录操作人、时间、备份文件名、恢复前后数据量

### 禁止事项
- ❌ 禁止直接覆盖数据库而不先备份当前数据
- ❌ 禁止从备份目录之外的任意路径恢复
- ❌ 禁止 viewer 执行恢复操作
- ❌ 禁止无审计日志的恢复操作
- ❌ 禁止在业务高峰期自动执行恢复

### 恢复后验证
- 自动运行维护安全检查（preflight）
- 验证关键表数据完整性
- 记录恢复前后的数据对比

### 服务重启
- SQLite 是文件级数据库，恢复后需要新的数据库连接才能生效
- 生产环境可能需要重启后端服务
- 需在文档中说明重启步骤

## 5. 推荐正式使用流程

### 日常操作流程

```
1. 每批正式产品录入后 → 创建数据库备份
2. 重要操作前（如批量编辑）→ 创建数据库备份
3. 每批次录入完成后 → 导出 CSV 反向核对
4. 定期检查备份文件完整性 → 使用恢复预检
```

### 出问题时的处理流程

```
1. 确认问题范围（影响多少产品/记录）
2. 运行恢复预检，确认可用的备份文件
3. 选择最合适的恢复时间点（最近且数据量正常的备份）
4. 按恢复流程执行（未来实现）
5. 恢复后运行维护安全检查
6. 补充恢复期间丢失的数据（如有）
```

### 备份命名规范

系统当前使用两种命名规范：

| 来源 | 格式 | 示例 |
|------|------|------|
| `/api/backups/manual` | `inventory-backup-YYYY-MM-DD-HHMMSS.db` | `inventory-backup-2026-07-03-140000.db` |
| `/api/maintenance/backups` | `inventory_backup_YYYYMMDD_HHMMSS.sqlite` | `inventory_backup_20260703_140000.sqlite` |

两种格式均可作为恢复候选，恢复预检对两者都支持。

## 6. 备份策略建议

| 场景 | 建议 |
|------|------|
| 日常开发/测试 | 每次重要操作前手动备份 |
| 正式环境试用期 | 每天至少 1 次备份 + 操作前备份 |
| 正式环境稳定期 | 每天 1 次备份 + 每周完整预检 |
| 紧急情况 | 操作前立即备份 |

### 备份文件管理
- 备份文件不会自动删除
- 建议定期清理过旧备份，保留最近 30 天的备份
- 重要节点备份应长期保留并导出到外部存储
