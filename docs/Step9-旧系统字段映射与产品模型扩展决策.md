## 1. 本轮背景

### 1.1 Step 9-2 的定位

Step 9-2 产出的 [产品/库存 CSV 导入模板设计](./Step9-产品库存CSV导入模板设计.md) 定义了 **7 个当前新系统可安全落库字段**：

| # | CSV 表头 | 数据库字段 |
|---|---------|-----------|
| 1 | SKU | `sku` |
| 2 | 产品名称 | `name` |
| 3 | 分类 | `category` |
| 4 | 当前库存 | `current_stock` |
| 5 | 最低库存 | `min_stock` |
| 6 | 单位 | `unit` |
| 7 | 存储位置 | `location` |

这 7 个字段是"当前新系统真实存在的列"——不是旧系统字段的上限，而是**当前系统有能力落库的最小安全子集**。

### 1.2 为什么需要 Step 9-2B

用户提供的旧系统截图和腾讯共享文档截图显示，**旧系统产品资料字段明显比当前新系统更丰富**：

- 腾讯共享文档包含 **10 个字段**（含品牌、中文描述、图片、备注等）
- 旧库存系统页面包含 **9 个字段**（含品牌、规格、产品图片等）
- 当前新系统仅 **7 个用户可写字段**

如果正式替换旧系统时只迁移这 7 个字段，将丢失品牌、规格、描述、备注、图片等**重要的业务信息**。这些信息在日常库存管理、采购申请、产品检索中都有实际使用价值。

### 1.3 本文档的定位

**不是推翻 Step 9-2**，而是在看到旧系统完整字段后，做出以下补充决策：
1. 哪些旧字段可以**直接映射**到当前新系统字段 → 导入即可
2. 哪些旧字段当前新系统**不存在**但建议**未来扩展** → 暂存原始数据，后续落库
3. 哪些旧字段**不应导入**而应由新系统**自动计算** → 标记为忽略/仅供参照
4. Step 9-3 后端 CSV 预览接口应支持哪些**中文表头别名**
5. 是否应该在后续步骤中**扩展 products 表**

## 4. 字段优先级决策

### 4.1 P0：第一版必须支持落库（Step 9-3 ~ 9-5）

这些字段直接写入当前 `products` 表，无需任何数据库模型变更。

| 旧字段名 | → 新系统字段 | 处理逻辑 |
|---------|-------------|---------|
| 产品货号 | `sku` | 直接映射，去空白，SKU 唯一性校验 |
| 产品名称 | `name` | 直接映射，去空白，超长截断（>100 字符） |
| 类别 | `category` | 直接映射，空值默认"耗材"，非已知值警告 |
| 当前库存 | `current_stock` | 直接映射，非负整数校验，作为期初库存 |
| 最低库存 | `min_stock` | 直接映射，非负整数校验，空值默认 0 |
| 单位 | `unit` | 直接映射，空值默认"个"，超长截断 |
| 存放位置 | `location` | 直接映射，可为空 |

**结论**：P0 字段覆盖了**旧系统最核心的业务数据**（产品标识、名称、分类、库存数量、位置），可以满足基本的库存管理需求。但会丢失品牌、规格、描述等增强信息。

### 4.2 P1：正式替换旧系统强烈建议支持（需扩展模型）

这些字段在旧系统中存在且具有实际业务价值，建议在正式替换前完成模型扩展。

| 备注 | `notes` | Text, nullable | 临时备注、特殊说明 | 低 — 单列新增 |

## 5. 产品模型扩展决策建议

### 5.1 建议：正式替换前扩展 products 表

**核心判断**：旧系统的品牌、规格、描述、备注、图片字段在实验室库存管理场景下**不是装饰性字段**，而是有实际业务价值的：

- **品牌**：同类型耗材/试剂存在多品牌供应商，品牌是采购和领用的关键检索维度
- **规格**：化学品（如"丙酮 500mL" vs "丙酮 1L"）、刀具（如"D6×50" vs "D6×100"）需要通过规格区分
- **中文描述**：化学试剂的安全说明、存储条件、有效期限等需要长文本承载
- **备注**：临时停产、替代品、批次信息等非结构化信息
- **图片**：产品实物图片辅助识别，减少拿错物料的情况

**建议**：在 Step 9-3 或 Step 9-5 之前（即实际导入接口实现之前），先扩展 products 表。建议新增 5 个字段：

```python
# apps/api/database.py Product 模型新增

brand = Column(String(50), nullable=True)          # 品牌
specification = Column(String(50), nullable=True)   # 规格/型号
description = Column(Text, nullable=True)           # 中文描述
notes = Column(Text, nullable=True)                 # 备注
image_url = Column(String(255), nullable=True)      # 产品图片链接
```

**扩展时机建议**：

```
Step 9-3A   后端 CSV 预览接口（仅 P0 落库预览，识别 P1 字段并提示"暂不保存"）
    ↓
Step 9-3B   产品模型扩展方案评审（确认 5 个新字段的类型/长度/默认值）
    ↓
Step 9-3C   执行 products 表扩展（新增列 + migrate 函数 + schema 更新）
    ↓
Step 9-4    前端 CSV 上传与预览页面（预览表展示 P0+P1 全部字段）
    ↓
Step 9-5    正式导入执行接口（P0+P1 全部落库）
```

如果选择**不分步扩展**（即暂不扩展 products 表，只导入 P0 7 字段），则：
- 导入时将 P1 字段的原始值写入 `audit_logs.details`（JSON 格式保留）
- 后续扩展模型后，可从审计日志中找回 P1 数据重新导入
- 代价：额外的数据恢复操作，且原始 CSV 需同时保留

### 5.2 不建议在本轮实现

根据 Step 9 系列设计文档的节奏，**本轮（9-2B）仅做决策建议，不做任何代码修改**。具体扩展实施建议放在 Step 9-3B。

## 6. Step 9-3 CSV 预览接口的别名识别建议

### 6.1 设计目标

CSV 文件的表头名称不应要求用户严格匹配新系统内部字段名。系统应能识别常见别名——无论是来自腾讯共享文档、旧库存系统、手动整理的 Excel，还是其他 ERP 系统导出。

### 6.2 字段别名映射表

以下别名映射表供 Step 9-3 后端 CSV 预览接口实现时参考：

| 规范字段 | 中文主表头 | 中文别名（按优先级排列） | 英文别名 |
|---------|-----------|---------------------|---------|
| `sku` | `SKU` | `产品货号`、`货号`、`产品编号`、`商品编号`、`物料编码`、`产品代码` | `sku`、`SKU`、`product_code`、`item_code`、`material_code` |
| `name` | `产品名称` | `商品名称`、`物料名称`、`名称`、`品名` | `name`、`product_name`、`item_name` |
| `category` | `分类` | `类别`、`产品类别`、`物料组`、`产品分类`、`品类` | `category`、`product_category` |
| `current_stock` | `当前库存` | `库存数量`、`现有库存`、`库存`、`当前库存数量`、`在库数量` | `current_stock`、`stock`、`quantity`、`qty` |
| `min_stock` | `最低库存` | `预警库存`、`安全库存`、`最低阈值`、`库存下限`、`最小库存` | `min_stock`、`safety_stock`、`reorder_point` |
| `unit` | `单位` | `计量单位`、`基本单位`、`包装单位` | `unit`、`uom`、`unit_of_measure` |
| `location` | `存储位置` | `位置`、`存放位置`、`仓库位置`、`库位`、`货架`、`仓位` | `location`、`storage_location`、`bin` |
| `brand` | `品牌` | `商标`、`厂牌`、`制造商` | `brand`、`manufacturer` |
| `specification` | `规格` | `型号`、`规格型号`、`产品规格` | `model`、`specification`、`spec` |
| `description` | `中文描述` | `描述`、`产品描述`、`详细描述` | `description`、`desc` |
| `notes` | `备注` | `附注`、`说明` | `notes`、`remark`、`comment` |
| `image_url` | `图片` | `产品图片`、`图片链接`、`图片地址` | `image`、`image_url`、`picture` |

### 6.3 别名匹配规则

1. **精确匹配优先**：先尝试与规范中文表头精确匹配
2. **中文别名匹配**：再尝试与中文别名列表匹配（不区分全角/半角、末尾冒号）
3. **英文别名匹配**：最后尝试英文别名（不区分大小写、下划线/连字符等效）
4. **模糊匹配**：对于表头含有多余空格、前缀/后缀的情况，做 trim 后再匹配
5. **未匹配列**：记录到校验报告："未识别的列: `{原始表头}`"，不阻断流程
6. **重复匹配**：如果两个表头别名都指向同一个规范字段（如"产品名称"和"商品名称"同时出现），报错并让用户修正 CSV

### 6.4 P1 字段的特殊处理

在 Step 9-3 中（模型尚未扩展），P1 字段（品牌、规格、描述、备注、图片）的别名也被识别，但标记为：

> ⚠️ 字段 `{表头}` → `{规范字段}` 已识别，但当前系统暂不支持保存此字段。该数据将在导入报告中保留，待系统升级后可重新导入。

这样可以：
- 不丢失用户的旧数据
- 用户看到系统已"认识"这些字段，增强信心
- 明确告知哪些字段当前会落库、哪些暂存

## 7. 导入策略建议

### 7.1 两阶段导入策略

#### 第一阶段（Step 9-3 ~ 9-5）：最小安全导入

```
CSV 文件上传
    │
    ├── P0 字段（7 个）→ 校验 → ✅ 落库到 products 表
    │
    ├── P1 字段（5 个）→ 识别 → ⚠️ 暂存到 audit_logs.details（JSON）
    │                     提示："品牌、规格、描述、备注、图片暂不保存，原始数据已归档"
    │
    ├── P2 字段（旧状态、更新时间）→ 识别 → ℹ️ 导入报告中对比展示
    │
    └── 未识别的列 → 列出 → ℹ️ "以下列未识别：xxx"
```

#### 第二阶段（模型扩展后）：完整导入

```
CSV 文件上传（同一份或新的）
    │
    ├── P0 字段（7 个）→ 校验 → ✅ 落库
    │
    ├── P1 字段（5 个）→ 校验 → ✅ 落库到扩展后的 products 表
    │
    └── 全部字段落库，信息完整度 80%
```

### 7.2 原始 CSV 数据保留策略

**强烈建议**：无论导入到哪个阶段，**原始 CSV 文件内容不得丢弃**。

保留方式建议：
1. 导入时在 `audit_logs.details` 中存储完整的 JSON 格式行数据（含 P0+P1+P2 全部字段）
2. 导入完成后将原始 CSV 文件复制到 `apps/api/import-archive/` 目录（加入 `.gitignore`）
3. 导入报告中包含"下载原始数据"链接

这样即使第一阶段只落库了 7 个字段，后续扩展模型后仍可从归档数据中找回并重新导入 P1 字段。

## 8. 状态字段处理

### 8.1 旧系统"状态"字段

旧系统（腾讯共享文档）有"状态"列，其值可能是：
- "正常" — 库存充足
- "预警"/"低库存" — 库存不足
- "缺货" — 库存为 0
- 或其他自定义状态

### 8.2 新系统状态计算规则

新系统不使用静态存储的状态值，而是**每次读取时动态计算**：

```python
# apps/api/database.py line 85
status = "低库存" if current_stock <= min_stock else "正常"
```

### 8.3 处理策略

| 场景 | 处理方式 |
|------|---------|
| 导入预览 | 计算新系统状态 = f(current_stock, min_stock)，与旧系统状态对比，差异行在预览中标 ⚠️ |
| 导入执行 | **不导入旧状态**，落库后由系统自动计算 |
| 导入报告 | 列出"状态差异"：旧状态为"正常"但新系统计算为"低库存"的行，供人工复核 |

**示例**：

```
旧状态: 正常, 当前库存: 5, 最低库存: 10
→ 新系统计算: 低库存（5 ≤ 10）
→ 预览提示: ⚠️ 旧系统状态为"正常"，但按新系统规则应显示为"低库存"，请确认库存数量是否正确
```

### 8.4 不建议导入旧状态的原因

1. 新系统每次查询时动态计算状态，数据库中存储的 `status` 值在 `to_dict()` 中被**覆盖**（line 85）
2. 即使导入旧状态值，它也不会被任何读取路径使用
3. 保留旧状态作为参考值可能造成混淆（用户看到页面显示"低库存"但数据库存的是"正常"）

## 9. 图片字段处理

### 9.1 图片的三种存在形式

| 形式 | 旧系统场景 | 迁移难度 |
|------|-----------|---------|
| **链接/URL** | 腾讯共享文档中的在线图片链接 | 低 — 直接存为 `image_url` 文本 |
| **文件路径** | 旧系统文件服务器上的图片路径 | 中 — 需要图片文件同步迁移到新服务器 |
| **内嵌图片** | 腾讯文档单元格内插入的图片 | 高 — 需导出图片文件 + 建立文件名映射 |

### 9.2 建议策略

**第一阶段（不迁移）**：
- 如果旧系统图片字段是链接/URL，导入时暂存到 `audit_logs.details`
- 导入报告中列出"含图片的产品数"，提示图片暂未迁移
- 产品详情页暂不显示图片

**第二阶段（模型扩展后）**：
- 新增 `image_url` 字段（String(255)）
- 如果旧系统是链接，直接落库
- 如果旧系统是文件/内嵌，需要单独设计图片迁移流程：
  1. 从旧系统批量导出图片文件
  2. 按 SKU 或产品名称建立文件名映射
  3. 将图片文件放入新系统 `public/product-images/` 目录
  4. 在 `image_url` 中存储相对路径或完整 URL

**注意**：图片迁移是独立工程，不应与 CSV 数据导入混合。建议作为 Step 9 之后的一个独立子项目。

## 10. 更新时间字段处理

### 10.1 不建议覆盖系统字段的原因

| 新系统字段 | 用途 | 是否可覆盖 |
|-----------|------|-----------|
| `created_at` | 记录产品在新系统中的创建时间 | ❌ 不可覆盖 |
| `updated_at` | 记录产品最后一次被修改的时间 | ❌ 不可覆盖 |
| `last_updated` | `YYYY-MM-DD` 格式的展示用日期 | ❌ 不可覆盖 |

这三个时间戳字段由 SQLAlchemy 自动管理（`default=datetime.now`、`onupdate=datetime.now`），覆盖它们会：
- 丢失真实的数据创建/修改时间
- 与审计日志时间线不一致
- 违反"导入后由系统管理"的原则

### 10.2 处理建议

| 旧系统时间信息 | 处理方式 |
|--------------|---------|
| 旧系统"更新时间" | 作为 `source_updated_at` 记录在导入报告的每行详情中 |
| 旧系统"创建时间"（如有） | 作为 `source_created_at` 记录在导入报告中 |
| 导入时间 | 新系统自动写入 `created_at` 和 `last_updated`（导入当天的日期） |
| 数据溯源 | 在 `audit_logs.details` 中记录旧系统的时间信息，便于追溯 |

```python
def migrate_products():
    """为 products 表添加扩展字段（Step 9-3C）"""
    engine = create_engine(DATABASE_URL)
    with engine.connect() as conn:
        # 检查每列是否存在，不存在则新增
        for col_name, col_type in [
            ("brand", "VARCHAR(50)"),
            ("specification", "VARCHAR(50)"),
            ("description", "TEXT"),
            ("notes", "TEXT"),
            ("image_url", "VARCHAR(255)"),
        ]:
            result = conn.execute(
                text(f"PRAGMA table_info(products)")
            )
            existing_cols = [row[1] for row in result]
            if col_name not in existing_cols:
                conn.execute(
                    text(f"ALTER TABLE products ADD COLUMN {col_name} {col_type}")
                )
        conn.commit()
```
