# 库存自动化管理系统正式使用与日常维护指南

> 版本：V2/V3  
> 更新时间：2026-07-05  
> 适用范围：系统正式使用前验收、日常操作维护、异常排查和后续交接  

---

## 一、文档目的

本文档用于指导库存自动化管理系统的正式使用和日常维护，面向管理员和日常使用人员。文档内容涵盖：

- 正式使用前需要完成的检查
- 每日或每次使用前建议的快速检查
- 产品录入、出入库、低库存预警等核心业务流程操作规范
- 用户权限与账号管理
- 数据安全与备份原则
- 常见异常处理
- 正式切换旧系统相关建议

本文档不是开发文档，不包含安装、编译、接口开发等技术内容。

## 二、正式使用前检查清单

以下检查应在系统正式投入使用前逐项完成：

### 基础运行检查

| 编号 | 检查项 | 说明 |
|------|--------|------|
| 1 | Git 状态 | `git status -sb` 工作区应为 clean |
| 2 | 前端端口 | 5173，确认未被占用 |
| 3 | 后端端口 | 8000，确认未被占用 |
| 4 | 前端构建 | `npm run build` 通过 |
| 5 | API 配置 | `npm run check:api-config` 通过 |
| 6 | 浏览器访问 | 能正常打开登录页并登录 |

### 数据完整性检查

| 编号 | 检查项 | 说明 |
|------|--------|------|
| 1 | 产品数据核对 | 进入产品管理页，确认已有产品数据完整、核对状态合理 |
| 2 | 出入库记录 | 进入出入库记录页，确认记录正常、无异常数据 |
| 3 | 低库存预警 | 进入低库存预警页，确认预警数量与实际库存状态一致 |
| 4 | 操作日志 | 进入操作日志页，确认操作记录完整可追溯 |
| 5 | 仪表盘 | Dashboard 各项统计数据显示正常 |
| 6 | 用户权限 | 确认 admin 和 viewer 权限正常 |

### 备份与安全检查

| 编号 | 检查项 | 说明 |
|------|--------|------|
| 1 | 数据库备份 | 在系统设置中执行一次安全检查并创建数据库备份 |
| 2 | 备份文件确认 | 确认备份文件已生成，可在备份记录中查看和下载 |
| 3 | 备份恢复预检 | 如有备份文件，可执行恢复预检确认备份可读（只读检查，不恢复） |

## 三、每日或每次使用前快速检查

以下为日常使用的建议检查项，不必全部执行，根据实际情况选择性检查：

| 检查项 | 验证方式 | 频率 |
|--------|----------|------|
| Dashboard 是否正常 | 打开仪表盘，确认统计数据加载正常 | 每次打开系统时 |
| 产品查询是否正常 | 在产品管理页搜索一个已知产品 | 每次使用产品管理前 |
| 低库存预警 | 打开低库存预警页，确认预警列表与预期一致 | 每天一次 |
| 出入库记录 | 打开出入库记录页，确认最新记录正确 | 每次操作出入库前 |
| 操作日志 | 打开操作日志页，确认最新操作已记录 | 不定时抽查 |
| 控制台报错 | 打开浏览器 DevTools Console，确认无红色报错 | 发现异常时 |

## 四、正式录入产品前注意事项

### 必填字段

- **产品名称**：必须填写，建议使用规范名称，统一命名风格
- **SKU 编码**：必须填写，建议全局唯一，格式建议统一（如 PRD-YYYYNNNN）
- **库存分类**：从下拉选择（2楼库存、3楼库存等）
- **单位**：从下拉选择（个、盒、瓶、包、套）
- **当前库存**：准确填写当前实际库存数量
- **最低库存**：填写合理的预警阈值

### 建议填写的管理字段

- **存储位置（库位）**：根据库存分类联动，精确到货架
- **品牌**：如安捷伦等
- **规格**：如 1.5×100mm
- **供应商**：如上海某某化工

### 可选填写的价格字段

- 采购价、售价如果暂时未知，可以留空
- 不建议用 0 代表未知价格，0 表示免费或零价格，留空表示未知
- 价格缺失不会影响产品保存，也不会影响库存管理

### 核对状态说明

产品管理页面中的「核对状态」用于辅助管理员判断产品资料完整性：

- **信息完整**：核心字段基本完整，可用于正式库存管理
- **建议补充**：产品可以保存和查询，建议后续补充辅助信息
- **需核对**：缺少关键字段，建议优先核对后再正式使用

核对状态仅作为提示，不会强制阻止保存。

### 产品名称和 SKU 重复提示

- 系统会实时检查 SKU 是否重复，重复时会给出红色提示
- 产品名称重复时给出黄色轻提示（允许同名不同规格）
- 如果名称和规格同时重复，提示可能是重复录入

## 五、出入库操作注意事项

### 入库

- 用于记录实际到货、盘盈、补充库存等场景
- 录入入库后，产品当前库存自动增加
- 建议填写备注，说明入库来源（如供应商、入库单号）

### 出库

- 用于记录实际领用、销售、消耗等场景
- 录入出库后，产品当前库存自动减少
- 出库前系统会校验库存是否充足
- 建议填写备注，说明出库用途（如领用人、用途）

### 撤销交易

- 已完成的出入库记录可以撤销
- 撤销操作会按原交易方向回滚库存
- 撤销后交易状态变为"已撤销"
- 已撤销记录仅用于历史追溯，不再参与有效库存变动
- 撤销操作不可逆，请确认后再执行

### 不建议的操作

- 不要为了修改库存数字而随意删除交易记录
- 不要用出库操作清空错误产品，应通过编辑产品来修正
- 发现库存异常时，先查看产品台账和操作日志，确认原因后再操作

## 六、低库存预警处理流程

### 预警原理

低库存预警由系统根据产品当前库存与最低库存的比值自动生成：

- 库存 ≤ 最低库存的 20%：紧急预警
- 库存 ≤ 最低库存的 50%：中等预警
- 库存 ≤ 最低库存：较低预警

### 处理流程

1. **发现预警**：在低库存预警页面或 Dashboard 查看预警列表
2. **查看详情**：点击"查看详情"了解产品完整信息和库存比例
3. **生成提醒**：点击"补货提醒"生成可复制的提醒内容
4. **通知负责人**：将提醒内容发送给采购负责人确认
5. **执行入库**：实际到货后，通过出入库记录执行入库

### 重要说明

- 低库存预警不会自动修改库存数量
- 系统不会自动生成采购单
- "补货提醒"只是生成一段提醒文本，方便通知采购负责人
- 建议结合公司实际采购流程使用

### 建议补足数量的计算方式

补货提醒中建议补足数量 = 最低库存 - 当前库存（如结果为负数则显示 0），仅供采购决策参考，实际补货量由采购负责人根据实际需求确定。

## 七、用户权限与账号管理

### 角色说明

| 角色 | 权限范围 |
|------|----------|
| 管理员（admin） | 新增、编辑、删除产品；录入出入库；撤销交易；创建数据库备份；导出 CSV；执行恢复预检；管理用户账号（新增/编辑/停用/重置密码） |
| 只读用户（viewer） | 查看产品列表和库存状态；查看出入库记录和台账；查看操作日志；查看仪表盘和低库存预警；查看备份状态 |

### 账号管理建议

- 管理员账号数量不宜过多，建议 2-3 个
- 停用账号前请确认该用户不再需要使用系统
- 重置密码后请及时通知对应用户
- 管理员账号和涉及老板级别的账号需要重点保护
- 不要让多人共用一个管理员账号操作，不利于操作追溯

## 八、数据安全与备份原则

### 备份原则

- **大操作前先备份**：批量录入产品、清空业务数据、恢复准备等操作前先创建备份
- **定期备份**：建议每批产品录入完成后、每天收工时各创建一次备份
- **保留多份**：不要只保留一份最新备份，保留多份不同时间点的备份
- **下载存档**：重要备份可下载到本地电脑保存

### 安全红线

以下操作绝对不能执行：

- 不要直接删除或手动修改数据库文件（.db / .sqlite）
- 不要覆盖已有的备份文件
- 不要把数据库文件（.db / .sqlite / .csv / backups）提交到 Git
- 不要在没有备份的情况下执行清空或恢复类操作
- 不要在不确定的情况下执行恢复操作

### 导出与核对

- 导出 CSV 用于与外部数据来源逐条比对
- 导出前系统会自动运行安全检查
- 管理员可选择"创建备份后导出"以确保导出时数据已备份

### 关于清空业务数据

- "危险维护操作"中的清空业务数据功能，仅供管理员在确认备份和数据来源后使用
- 系统会先自动创建备份，成功后才执行清空
- 清空后用户账号、系统设置和备份文件不会受影响
- 正式使用系统后，一般不需要使用此功能

## 九、异常情况处理建议

### 页面打不开或白屏

1. 刷新浏览器页面（F5）
2. 检查前端开发服务器是否在运行（端口 5173）
3. 检查后端服务是否在运行（端口 8000）
4. 打开浏览器 DevTools Console 查看是否有红色报错

### 数据不刷新

1. 刷新页面（F5）
2. 确认当前在正确的页面和时间范围内
3. 如产品数据不刷新，检查筛选条件是否过于严格

### 库存数字异常

1. 打开该产品的"台账"查看历史出入库记录
2. 打开操作日志查看是否有异常的编辑或删除操作
3. 确认最近是否有撤销操作
4. 不要直接修改库存数字，优先通过出入库记录来调整

### 后端接口异常

1. 确认后端服务已启动（端口 8000）
2. 如持续报错，联系系统管理员或技术人员排查
3. 系统前端会自动降级使用本地数据缓存

### 登录异常

1. 确认用户名和密码正确
2. 确认账号未被停用
3. 管理员可在用户管理中重置密码
4. 如忘记管理员密码，需由另一位管理员协助重置

## 十、正式切换旧系统前建议

### 切换前准备

1. 旧系统继续保留一段时间作为只读参考
2. 在新系统中完成所有正式产品数据录入
3. 导出新系统 CSV 与旧系统数据进行逐条核对
4. 试运行一段时间（建议至少一周），在实际使用中验证
5. 确认出入库流程已适配公司日常操作习惯
6. 确认备份功能正常，至少保留两份可用备份

### 切换验收

1. 产品数量与旧系统一致
2. 各品牌/分类产品数量与预期一致
3. 库存数量与实物核对无误
4. 低库存产品列表与旧系统/实际情况一致
5. 管理员和只读用户均可正常登录和操作
6. 备份文件可正常下载和恢复预检

### 切换后

1. 旧系统转为只读归档，不再新增或修改数据
2. 新系统作为唯一正式的库存管理工具
3. 如切换后发现数据问题，可通过备份和恢复流程处理

## 十一、后续维护原则

### 日常维护

- 小步修改，一次只改一个模块
- 每次改动后执行 `npm run build` 确认构建通过
- 每次改动后执行 `npm run check:api-config` 确认 API 配置
- 重要节点提交 Git，写好 commit 信息
- push 前确认工作区状态为 clean

### 长期维护建议

- 不做无备份的大范围重构
- 新增功能优先保证不破坏已有功能
- 保持系统克制简约的风格，不为了"高级感"堆砌装饰
- 接口和数据模型变更前先确认影响范围
- 维护人员变更时，本文档和 `CLAUDE.md` 是核心交接文档

### 依赖更新注意

- 更新依赖前先创建备份
- 更新后执行完整回归检查
- 确认前端构建和 API 配置检查通过
- 确认所有核心页面正常显示
